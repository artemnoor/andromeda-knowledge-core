ontology, knowledge, sources, provenance, temporal metadata, rules, derived
values, dependencies, reviews and audit events.

PostgreSQL as source of truth, normalized critical fields and JSONB only for

## Task 4: Define normalized schema and migration

### Intent

Make the logical graph and temporal/provenance invariants durable without
letting an ORM schema become the domain model.

### Implementation Steps

1. Define tables for `ontology_versions`, `object_types`, `property_definitions`,
   `relation_types`, `ontology_change_proposals`, `knowledge_objects`,
   `sources`, `source_documents`, `provenance_records`, `observations`,
   `facts`, `relations`, `rules`, `rule_test_cases`, `derived_values`,
   `dependencies`, `review_items`, `audit_events`, and `change_events`.
2. Use text UUID identifiers generated by the application to keep the same
   repository portable to SQLite tests; use `timestamptz` in PostgreSQL.
3. Store typed fact columns (`value_type`, JSON value and queryable scalar
   projections) with validation in the domain. Do not make arbitrary JSON the
   only fact representation.
4. Add foreign keys and targeted indexes: natural source checksum, observation
   idempotency, fact subject/property/valid time, relation subject/type/object,
   active rule status/scope, dependency source and derived result key, review
   status and audit timestamp.
5. Add checks for status values, non-negative confidence, valid temporal
   intervals and optimistic-lock versions.

### Required Interfaces and Contracts

- `valid_to > valid_from` when both are supplied.
- `transaction_to` is null for the current knowledge version; historical
  versions are never physically deleted by normal mutations.
- `facts` and `derived_values` are separate tables with no polymorphic table
  that could blur their meaning.
- `dependencies` uses `source_kind/source_id` and `target_kind/target_id` and
  has indexes for reverse lookup.

### Error Handling and Logging

Migration failures fail the container startup. Repository constraint failures
are translated into stable domain conflict errors; never log full applicant
context or raw DSL payloads at INFO.

### Tests

- `alembic upgrade head` on an empty PostgreSQL database in CI/compose.
- Migration metadata includes all required tables and indexes.
- Invalid intervals and negative confidence are rejected.

### Acceptance Criteria

An empty database can reach head without `create_all`, and the schema supports
the domain relationships and temporal queries described by the API.

### Verification

- `alembic upgrade head`
- `pytest -q tests/integration/test_persistence.py`

## Task 5: Implement temporal/provenance repository ports

### Intent

Expose a small, swappable interface for the application/domain to store and
query facts, relations, rules and derived dependencies.

### Implementation Steps

1. Define protocol interfaces for source/observation/fact/relation repositories,
   ontology/rule repositories and derived/dependency/audit/review repositories.
2. Define temporal query methods that require an explicit axis (`valid_time` or
   `transaction_time`) and timestamp.
3. Map ORM rows to typed domain DTOs and back; keep SQLAlchemy models out of
   domain modules.
4. Use atomic upsert/natural identity checks for source ingestion and facts.
5. Use optimistic locking (`row_version`) for rule and ontology transitions.

### Required Interfaces and Contracts

- `find_facts(subject_id=None, property_code=None, as_of=None, known_as_of=None)`
  applies valid and transaction predicates independently.
- Repositories accept a unit-of-work/session from the application service; no
  repository commits halfway through activation.
- `get_or_create_by_idempotency` returns the prior accepted object on retry.

### Error Handling and Logging

Translate stale version updates to `CONCURRENT_MODIFICATION` (HTTP 409),
duplicate natural identities to idempotent success where policy allows, and
unknown IDs to `NOT_FOUND`.

### Tests

- A fact valid in 2027 but received in 2028 is excluded by valid-time 2026 and
  visible by transaction-time 2029.
- A later correction preserves the historical transaction version.
- Duplicate checksum/idempotency submissions return one logical observation.

### Acceptance Criteria

The same domain use case can run against SQLite test repositories and
PostgreSQL adapters without changing domain code.

### Verification

- `pytest -q tests/integration/test_persistence.py -k 'temporal or idempot'`

## Task 6: Add repository tests and migration checks

### Intent

Lock down the persistence contract before application modules depend on it.

### Implementation Steps

1. Build async fixtures that create a fresh database schema for unit/integration
   tests using the test adapter, while migration tests execute Alembic.
2. Cover foreign-key integrity, indexes/constraints, temporal filters,
   optimistic version checks and atomic idempotent inserts.
3. Add a migration smoke command to CI and Docker health workflow.

### Required Interfaces and Contracts

Tests must observe behavior via repository interfaces and public migration
commands; they may inspect metadata only in migration-specific checks.

### Error Handling and Logging

Test failures include table/constraint names and correlation IDs where an API
path is involved; fixture teardown always closes engines.

### Tests

This task is itself test-focused; all scenarios above are mandatory.

### Acceptance Criteria

Persistence tests fail if a future schema change removes temporal, provenance,
dependency or optimistic-locking guarantees.

### Verification

- `pytest -q tests/integration/test_persistence.py`
- `alembic check`

## Phase Risks and Mitigations

- Risk: SQLite differs from PostgreSQL JSON/temporal semantics. Mitigation:
  keep production migration smoke tests in Compose and constrain test queries
  to portable SQLAlchemy expressions.
- Risk: overly generic provenance JSON. Mitigation: normalize source,
  observation and evidence locator references into dedicated columns/tables.
